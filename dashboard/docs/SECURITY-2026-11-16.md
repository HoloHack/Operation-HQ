Status: prepared for review and CI, not a production deployment. Existing Site 13 (`f8f47b6be01b58983401f4b9d6ddc4f7fb2066b7`) and personal records are unchanged. Keep this work separate from companion PR17.

## Evidence and minimum compatible patch

| Component | Existing | Candidate |
|---|---|---|
| Next / matching ESLint tooling | 16.4.1 | 16.4.5 |
| React / React DOM / project RSC | 19.2.8 | 19.2.9 together |
| Vite RSC plugin | 0.5.26 | 0.5.38 |
| Vinext | 1.0.0-beta.5 | 1.2.0 |

The top-level RSC patch alone is insufficient: plugin-rsc has its own vendored decoder. Candidate plugin0.5.38 actually vendors RSC19.3.1; project RSC resolves19.2.9. Both are checked by the new security-pin tests. Published peer ranges accept this coordinated set; no React19.3 project upgrade or unrelated framework switch is introduced. The lockfile is regenerated and the frozen dependency install succeeds. Much lockfile churn is peer-qualified React references, not justification to blindly upgrade every package.

Primary sources checked 16 November:

- [React critical RSC advisory](https://github.com/react/react/security/advisories/GHSA-xqc2-xf4c-x3h3): includes project19.2.8, fixes19.2.9. Exposure depends on framework/RSC handling; tests passing cannot clear a known vulnerable decoder.
- [Plugin-RSC critical advisory](https://github.com/vitejs/vite-plugin-react/security/advisories/GHSA-59pf-q495-3c99): plugin versions below0.5.38 include affected vendored code.
- [Vinext closure-binding advisory](https://github.com/cloudflare/vinext/security/advisories/GHSA-8969-277p-8rrm): fixed1.2.0, with a coordinated plugin update required.
- [Vinext cache-key advisory](https://github.com/cloudflare/vinext/security/advisories/GHSA-2956-r8mj-w5c4): fixed1.2.0; the separate affected @vinext/cloudflare adapter is not in this lockfile.
- [Next16.4.5 release](https://github.com/vercel/next.js/releases/tag/v16.4.5): November fixes. No application-defined use-cache/Server Actions were found in the source scan, but absence of those application patterns is not blanket production immunity.

## Verification and remaining gates

- Fresh unchanged application regressions:126/126 pass; typecheck and production build pass with the coordinated installed versions.
- Two new security-pin tests pass: exact manifest/installed version agreement, exclusion of old project RSC/plugin/Vinext lock references, and the plugin's actual vendored decoder version.
- Full dependency audit returns zero critical, five high, eleven moderate and three low findings. The five high findings are development tooling: Vite's Windows launch-editor issue and four Undici findings through Miniflare/Wrangler. They are not silently declared harmless; assess and patch them in a bounded follow-up. Vite8.1.6 and Undici7.30.1 are the audit's indicated fixed versions, not already-installed fixes.
- Production-only audit returns zero high/critical, two moderate and two low findings. This narrower audit is not proof that bundled development/build dependencies are safe; that is why the vendored decoder was explicitly checked.
- Require fresh CI on Node24 and minimum Node22.13, all regression/type/build gates, the complete dashboard Chromium sweep, authentication/account-isolation behavior, and independent review before promotion. The browser fixture is useful interaction evidence, not owner sign-in or real-provider acceptance. Real production SSR/hydration smoke acceptance must also be retained before replacing Site13.
- No personal database, permission, audience, model, OAuth identity or schema changes are needed. Local browser execution was previously blocked by environment socket policy; do not bypass it.
